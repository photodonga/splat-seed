# 리플레이 코드 → NPLN ID 조회 기술 조사

조사일 2026-10-30. 브랜치 `research/replay-npln-lookup`. 코드 구현 없음(조사 문서만).

## 결론 요약

| 질문 | 답 |
|---|---|
| 리플레이 코드만으로 NPLN ID를 얻을 수 있는가 | **기술적으로는 가능.** SplatNet 3의 리플레이 검색 결과 ID 안에 업로더의 NPLN ID가 들어 있다. 단, 조회 자체에 닌텐도 인증이 필요하다 |
| 인증이나 서버가 필요한가 | **둘 다 필요.** 닌텐도 계정(NSO 앱 로그인) 인증, 그리고 그 인증 정보를 숨겨 둘 서버. GitHub Pages만으로는 불가능 |
| 실제 작동하는 최소 구현을 만들었는가 | **아니오.** 이 환경에는 닌텐도 계정·NSO 이용권·실제 리플레이 코드가 없고, 닌텐도 서버로 나가는 네트워크도 막혀 있어 조회를 한 번도 실행하지 못했다. 검증하지 못한 백엔드 코드는 넣지 않았다 |
| 유지보수·비용·보안 문제 | 아래 "위험" 참고. 핵심은 운영자 계정 정지 위험, 앱 버전이 바뀔 때마다 깨지는 `f` 값 생성, 외부 `f` 생성 서비스 의존 |
| 다음 단계 | 아래 "선택지"에서 방향을 정한 뒤, 테스트용 닌텐도 계정과 실제 리플레이 코드로 조회부터 실증 |

## 1. Leanny의 기존 구조 (공개 소스맵 기준)

- 설정 화면에서 리플레이 코드(16자)를 받으면 브라우저가 외부 API를 호출한다.
  `https://splatoon3-replay-lookup.fancy.org.uk/api/splatnet3/replay/<코드>`
- 응답의 `npln_user_id`를 시드 키로 저장한다. 이 값으로 `<ID>_Lot_0..3`을 해시해 초기 상태를 만든다.
- 즉 Leanny도 **ID 조회는 자체적으로 하지 않고**, 다른 사람이 운영하는 서버에 맡긴다.

## 2. splatoon3-replay-lookup 분석

저장소: `samuelthomas2774/splatoon3-replay-lookup` (마지막 커밋 2023-03-06, **LICENSE 파일 없음** → 코드 재사용 근거 없음)

- Express 서버 하나. 내부적으로 `nxapi` 라이브러리의 SplatNet 3 클라이언트를 쓴다.
- 서버 운영자의 닌텐도 계정(`NA_USER_ID`, 저장된 세션)으로 SplatNet 3 GraphQL `DownloadSearchReplayQuery`를 호출한다.
- 응답의 `replay.id`(base64)를 풀면 `Replay-u-<20자>:<리플레이코드>` 형식이고, 여기서 `u-<20자>`를 NPLN ID로 꺼낸다.
  - 따라서 리플레이 코드 하나는 **업로더 한 명**의 ID만 준다. "리플레이 속 플레이어 중 본인 선택" 단계는 필요 없다. 본인이 올린 리플레이 코드를 넣으면 된다.
- README: 이 공개 API는 **Leanny 사이트 전용**이며, 다른 용도는 운영자에게 따로 문의하라고 명시.
- 운영 상태 페이지(nxapi-status)에는 조사 시점에 "Splatoon 3 replay lookup API"가 **중단(uptime 0%)**으로 표시됐다. 페이지 표시가 일부 서로 맞지 않아 단정하기는 어렵지만, 지금 Leanny의 리플레이 코드 기능도 작동하지 않을 가능성이 있다.

## 3. SplatNet 3 인증 구조

SplatNet 3에는 공개 API가 없다. 모든 도구(nxapi, s3s 등)는 닌텐도 스위치 온라인 앱의 로그인 과정을 재현한다.

1. 닌텐도 계정 로그인 → `session_token` (장기 보관되는 사실상의 계정 자격증명)
2. `session_token` → `id_token`
3. `id_token` → **`f` 값 생성.** NSO 앱 내부에서만 계산되는 값이라, 실제 안드로이드 앱에 Frida를 붙여 계산하는 별도 서버가 필요하다(nxapi-znca-api, imink 등)
4. `f` + `id_token` → Coral(NSO 앱) 로그인 토큰 → 게임 웹서비스 토큰(gtoken, 약 6시간) → SplatNet 3 bulletToken(약 2시간)
5. bulletToken으로 SplatNet 3 GraphQL 호출

추가로 확인한 사실:
- 2025년 6월부터 nxapi의 `f` 생성 서버는 **클라이언트 등록(nxapi-auth OAuth)**을 요구한다. 라이브러리로 직접 쓰려면 등록이 필요하다.
- `f` 생성은 NSO 앱 버전에 묶여 있어, 앱이 업데이트되면 생성 서버도 갱신돼야 한다.
- nxapi 문서: 2023-09에 SplatNet 3 접근이 일부 계정에서 예고 없이 차단된 사례 보고(401 `ERROR_INVALID_GAME_WEB_TOKEN`).
- nxapi 라이선스는 **AGPL-3.0** — 수정해 네트워크 서비스로 운영하면 소스를 공개해야 한다(우리 저장소는 공개이므로 충족 가능).
- SplatNet 3를 쓰려면 운영 계정에 NSO 이용권이 필요한 것으로 알려져 있다(**이번 조사에서 직접 확인하지 못함**).

## 4. GitHub Pages만으로 안 되는 이유

- 인증 토큰을 브라우저 코드에 넣으면 누구나 꺼내 쓸 수 있다.
- 닌텐도 서버는 브라우저 교차 출처 요청(CORS)을 허용하지 않는다.
- `f` 값은 브라우저에서 계산할 수 없다.

→ 최소한 **토큰을 보관하고 SplatNet 3를 대신 호출하는 서버 하나**가 필요하다. 사이트(GitHub Pages)는 그대로 두고, 서버는 "리플레이 코드 → NPLN ID" 하나만 응답하는 구조가 가능하다.

## 5. 선택지 비교

| 안 | 내용 | 사용자 경험 | 독립성 | 위험 |
|---|---|---|---|---|
| A. 자체 조회 서버 + 운영자 계정 | 우리 서버가 운영자 닌텐도 계정(전용 보조 계정 권장)으로 리플레이를 검색 | 목표와 같음 (코드 입력 → ID 자동) | 조회는 자체, **`f` 생성은 외부 서비스**(nxapi-znca-api 등록 필요) | 운영 계정 정지, 외부 `f` 서비스 중단, 앱 업데이트 대응 |
| B. A + `f` 생성까지 자체 운영 | 안드로이드 기기/에뮬레이터 + Frida로 `f` 직접 생성 | A와 같음 | 완전 자체 | 구축·유지 부담 큼, 상시 가동 기기 필요, 법적·약관 부담 가장 큼 |
| C. 사용자 본인 계정 연결 | 사용자가 자기 닌텐도 계정으로 로그인해 세션 토큰을 서버에 맡김 | 로그인 단계 추가 | A와 같음 | **세션 토큰은 계정 자격증명과 같음.** 지시한 "비밀번호 수집 금지"의 취지에 어긋나고 유출 시 피해 큼. 비권장 |
| D. ID·상태 직접 입력 (현재) | 사용자가 ID나 상태를 다른 경로로 얻어 입력 | 외부 도구 방문 필요 | 계산만 자체 | 목표 사용자 경험 미충족 |
| E. 기존 공개 조회 API 사용 | Leanny용 서버 호출 | 목표와 같음 | 외부 의존 | 운영자가 Leanny 전용이라고 명시, 현재 중단 표시. **사용 불가** |

현실적인 후보는 **A**다. B는 A가 안정된 뒤 `f` 의존을 없애야 할 때 검토한다.

## 6. 위험 (안 A 기준)

- **약관·계정:** SplatNet 3 비공식 접근은 닌텐도 이용약관상 회색지대다. 운영 계정이 차단될 수 있으므로 본계정이 아닌 전용 계정을 쓴다.
- **외부 의존:** `f` 생성 서비스가 멈추거나 등록 조건이 바뀌면 조회 전체가 멈춘다. "외부 서비스에 기대지 않는 독립"은 이 부분에서 달성되지 않는다.
- **유지보수:** NSO 앱·SplatNet 3 버전이 바뀔 때마다 nxapi 업데이트가 필요하다. 2023년 이후 갱신이 멈춘 replay-lookup 서버가 현재 중단 상태인 것이 그 예다.
- **보안:** 세션 토큰·OAuth 클라이언트 비밀은 서버 환경변수/비밀 저장소에만 둔다. 저장소·클라이언트 코드·로그에 남기지 않는다(nxapi는 디버그 로그에 토큰을 남길 수 있음).
- **남용·비용:** 공개 엔드포인트는 요청 제한·캐시(같은 코드 재조회 방지)·코드 형식 검증이 필요하다. 요청량이 적으면 소형 서버 비용은 작지만, nxapi(Node + 로컬 저장소)가 상시 돌아갈 서버가 필요하다. 서버리스 단일 함수로는 토큰 갱신·저장이 번거롭다.
- **개인정보:** NPLN ID는 계정 식별자다. 서버는 ID를 저장하지 않고 응답만 하며, 사이트도 ID를 저장하지 않는 현재 방침을 유지한다.

## 7. 엔진 통합 시 발견한 문제 (PR #2, 수정 안 함)

조회 결과 형식은 `u-` + 20자(예: `u-abcdefghij0123456789`)다. Leanny도 `u-`를 포함한 문자열 그대로 해시한다. 그런데 PR #2의 `initialState()`는 영문·숫자만 허용해 **실제 ID를 거부한다.**

```
initialState('u-abcdefghij0123456789')  → RangeError: NPLN user ID must be 6-64 ASCII letters/digits
```

통합 전에 PR #2에서 입력 검사를 `^u-[a-z0-9]{20}$` 형식으로 바꾸고, `u-` 포함 키로 Leanny 대조 벡터를 추가해야 한다. 엔진 변경이므로 승인 후 진행한다.

## 8. 검증하지 못한 것

- 실제 리플레이 코드 조회(계정·코드 없음, 이 환경에서 닌텐도 서버 접속 불가)
- 운영 계정에 NSO 이용권이 필요한지
- nxapi-auth 클라이언트 등록 조건과 이용 범위
- 조회 결과 ID로 만든 초기 상태가 실제 게임과 맞는지(별도 실기록 검증 필요)

## 9. 안 A로 갈 경우 필요한 것과 순서

1. 테스트용 닌텐도 계정(NSO 이용권 포함, 본계정 아님)과 직접 올린 리플레이 코드 1개 이상
2. nxapi-auth 클라이언트 등록 가능 여부 확인
3. 로컬에서 "리플레이 코드 → `replay.id` → NPLN ID" 한 번 실증 (여기까지 성공해야 구현 착수)
4. PR #2에서 `u-` ID 입력 검사 수정 + 대조 벡터 추가
5. 최소 서버(코드 형식 검사, 캐시, 요청 제한, 오류·토큰 만료 처리) 구현과 호스팅 결정
6. 사이트에 "리플레이 코드 입력" 단계 연결
